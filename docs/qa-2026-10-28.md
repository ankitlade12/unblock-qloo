# UNBLOCK product QA — October 28, 2026

## Scope and verdict

Test the organizer story from fictional participants and explicit taste consent through discovery, checked planning, approval, participant commitments, resource confirmation, export, disruption, repair, and evidence. Capture the actual interface on desktop, tablet, and mobile.

UNBLOCK feels coherent as an interactive product demonstration: the same people, preferences, constraints, decisions, and consequences carry through the story. It is a working prototype, not a production community service. Operations are synthetic, workspaces expire after 24 hours, and there are no real organizer accounts, participant invitations, ticket purchases, or transport bookings. Qloo discovery is live. The optional language-model assistant is unconfigured.

## Issues found and fixed

1. **Populated Evidence overflowed on mobile.** Long provider identifiers forced a 390 px viewport to 417 px. Identifiers now wrap and evidence timestamps stack on narrow screens. A populated-evidence browser regression protects this layout.
2. **An unsuccessful search looked like an untouched planner.** A zero-dollar budget correctly produced no plan, but the UI still invited the first search. Traces now record their input revision and result count. The empty state explains the outcome and offers a direct path to review inputs. Changing inputs clears this interpretation.
3. **Import validation exposed developer-oriented errors.** Invalid catalogue records now identify fields to check against the downloadable template and explain that existing catalogue data was preserved.
4. **Provider evidence text failed contrast checks.** The live, populated Evidence view exposed a pale identifier/date label. It now uses the readable secondary-text color, and the populated mobile fixture runs an axe accessibility check.
5. **An unavailable assistant occupied prominent space.** Its form is shown only when the model is configured. Deterministic planning remains available; readiness still reports actual configuration.

## Expanded live browser check

`scripts/browser_qa.cjs` requires `--allow-live`, uses one provider request, and writes screenshots plus a machine-readable check record. It verifies zero-budget feedback, safe invalid imports, reviewed-profile consent, recovery from an injected provider error, actual Qloo discovery, cache reuse, consent revocation, withdrawal/replanning, stale writes and final exports, populated Evidence on tablet/mobile, accessibility, workspace deletion, and browser exceptions.

The provider outage is injected into the QA browser. It is not a claim that Qloo failed. The participant withdrawal and choices are scripted fictional actions. The ordinary six-journey suite uses no provider calls; its long-identifier evidence record is a layout fixture.

## Realism and limits

The strongest demo sequence is **people → constraints → checked plan → confirmations → disruption → repair**. The repair makes the product's value visible: an operational change produces a new reviewed plan with an explicit cost and assignment difference. Discovery should be presented as widening choices; no improvement in attendance or community wellbeing has been measured.

Automated Chromium and axe checks do not establish usability for real participants. Safari, Firefox, physical devices, human screen-reader testing, high-load traffic, penetration testing, real provider bookings, live model execution, and longitudinal impact have not been verified. This audit covers the documented scenarios, not every possible input or failure.

Repeated QA runs can hit the intentional one-minute workspace-creation limit. Use a fresh isolated database locally or allow the rate window to expire when testing the public service; do not weaken the protection for testing.
