# Judge walkthrough

This is a synthetic demonstration, not evidence of measured community impact.

The recommended presentation is **Overview → Walk through the story**. Use the six chapters in order:

- **The people:** Meet Jordan, Morgan, and Taylor. Inspect real fields in the synthetic profiles.
- **Their choices:** Open **Test what discovery changes**, freeze the existing choices, record a fictional response, and compare the checked plans. Show the decision trail and export. Unchanged outcomes are valid; direct catalogue choices carry no Qloo claim. Return to the story. Change Jordan's interest. The counts update from current explicit responses. The guided Qloo setup shows the current credential, mapping, consent, and favorite prerequisites.
- **The possibilities:** Run checks and inspect computed results. The visual groups show who travels together, with companion seats included. Expand “Inspect times, access, and itemized costs” for the detailed itinerary. There is no guaranteed-success screen.
- **The commitments:** Open the exact proposal to approve and record each commitment and provider evidence. The story never records consent on behalf of the demo visitor.
- **The unexpected:** Cancel a resource used by an earlier proposal. Prior decisions become stale. Recheck the remaining options and inspect a repair or an honest infeasible result. Restore the synthetic offer if desired.
- **The evidence:** Read the actual current result, limitations, and visible delivery checklist.

For direct workspace exploration:

1. **Overview:** 12 fictional members, eight fictional screenings, a $300 organizer budget.
2. **Discover:** select Alex; change a response. Only Interested is eligible. Qloo discovery is visibly unavailable until a server key and reviewed mappings exist.
3. **Participants:** inspect Jordan's wheelchair and companion requirements. The companion uses both a seat and a ticket.
4. **Plans:** generate three checked alternatives where possible. Read coverage, exact costs, and unserved participants.
5. **Review:** approve an exact version; record each synthetic participant's commitment. Record evidence for the required seats and tickets from each synthetic provider.
6. **Export:** the final calendar becomes available only after every gate passes. Evidence JSON and provider drafts remain clearly labeled with their status.
7. **Disrupt:** mark a used resource unavailable, then replan. Prior approvals are invalidated. Review changed assignments and renew the exact-version approvals.
8. **No feasible result:** set the budget to $0 in Settings and generate again. The app reports constraints instead of weakening requirements.
9. **Evidence:** inspect the audit trail and limitations. Synthetic acceptance is not real acceptance; confirmation is not observed attendance.
